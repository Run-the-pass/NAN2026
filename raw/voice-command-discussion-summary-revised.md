# 음성인식 시스템 논의 정리

## 문서 목적

이 문서는 프로젝트에서 음성인식을 어떤 역할로 사용할지, 어떤 방식으로 발전시키려 했는지, 논의 과정에서 어떤 문제가 발견됐는지, 그리고 현재 펀테스트에서는 무엇을 검증하기로 했는지를 정리한다.

현재 음성인식은 단순한 입력 장치가 아니라 게임의 핵심 차별점으로 간주한다. 다만 논의 과정에서 제안됐던 **그룹·스쿼드 단위 명령은 현재 방향에서 기각됐다.** 따라서 이 문서는 개별 슬라임에게 내리는 명령과 한 명령 안에서 처리하는 작업 단위의 확장만을 다룬다.

---

## 1. 기존 음성인식 처리 구조

기존 문서에서 음성 명령은 다음 파이프라인으로 처리한다.

```text
마이크 입력
→ 오디오 녹음
→ Gemini 명령 해석
→ 명령 JSON 생성
→ 현재 게임 상태를 기준으로 검증
→ 세부 행동으로 분해
→ Phaser에서 슬라임 행동 실행
```

### 기본 원칙

- 주 처리 방식은 오디오에서 명령 JSON을 직접 생성하는 것이다.
- 실시간 자막은 디버깅용 참고 정보이며 실제 명령 입력으로 사용하지 않는다.
- Gemini는 사용자의 의도를 구조화한다.
- 실제 행동 순서, 유효성 판정, 작업 결과는 게임 코드가 결정한다.
- AI가 게임에 존재하지 않는 슬라임, 행동, 대상의 이름을 임의로 만들지 못하도록 후보를 제한한다.
- 인식된 명령은 현재 게임 상태와 대조해 실행 가능 여부를 검증한다.

### 예시 명령 형식

```json
{
  "status": "OK",
  "confidence": 0.94,
  "commands": [
    {
      "actorId": "slime-01",
      "action": "GET",
      "targetId": "green-herb-box",
      "destinationId": null,
      "sequence": 1
    }
  ],
  "reason": null
}
```

## 2. 음성인식을 넣는 이유에 대한 핵심 쟁점

가장 중요한 질문은 다음이었다.

> 마우스로도 가능한 행동을 굳이 음성으로 지시하는 것이 실제로 더 재미있거나 유리한가?

음성인식이 단지 클릭을 대체한다면 다음 문제가 생길 수 있다.

- 마우스보다 입력이 느리다.
- 정확한 명령 문법을 생각해야 한다.
- 인식 결과를 기다리는 동안 게임 흐름이 끊긴다.
- 처음에는 신기하지만 곧 불편한 기믹으로 느껴질 수 있다.
- 게임이 강제로 요구하기 때문에 쓰는 입력 수단이 될 수 있다.

따라서 음성인식은 최소한 다음 중 하나에서 분명한 가치를 가져야 한다.

- 여러 행동을 한 문장으로 묶을 수 있다.
- 세부 동작보다 작업의 목적을 직접 말할 수 있다.
- 플레이어가 직접 조작하는 사람보다 지휘하는 사람처럼 느끼게 한다.
- 슬라임이 자신의 말에 반응하는 모습 자체가 시청각적 재미를 준다.
- 동시에 진행되는 시설의 상태를 보며 다음 명령을 계획하게 한다.

---

## 3. ‘음성인식의 진화’라는 표현의 의미

논의 초반에는 ‘음성인식의 진화’라는 표현이 모호했다.

이 표현은 다음처럼 오해될 수 있었다.

- STT 정확도가 올라간다.
- 더 많은 단어를 인식한다.
- 자연어 처리 모델의 성능이 성장한다.
- 플레이어의 발음을 게임이 점점 더 잘 알아듣는다.

실제 의도는 기술적 인식률의 향상보다 다음에 가까웠다.

> 게임이 진행될수록 플레이어가 개별 슬라임에게 내릴 수 있는 명령의 작업 단위와 추상화 수준이 커진다.

더 정확한 표현은 다음과 같다.

- 음성 명령 체계의 확장
- 명령 단위의 확장
- 음성 지휘 업그레이드
- 명령 추상화의 성장

---

## 4. 현재 유효한 명령 확장 단계

그룹·스쿼드 명령은 제외하고, 개별 슬라임에게 내리는 명령 안에서만 단계가 확장된다.

### 1단계: 개별 단일 행동

특정 슬라임에게 하나의 행동을 지시한다.

```text
"말랑아, 초록 약초 가져와."
"말랑아, 양피지 가져와."
"말랑아, 가마솥으로 가."
```

게임 내부에서는 하나의 원자 행동으로 처리한다.

```text
GET(green-herb)
```

### 2단계: 개별 연속 명령

한 슬라임에게 여러 행동을 한 문장으로 연결해 지시한다.

```text
"말랑아, 초록 약초 가져와서 가마솥에 넣어."
```

게임 내부에서는 세부 행동으로 분해한다.

```text
GET(green-herb)
→ MOVE(cauldron)
→ PUT(green-herb, cauldron)
```

### 3단계: 개별 작업 명령

세부 행동 대신 목적이 있는 작업 단위를 지시한다.

```text
"말랑아, 재료 준비해."
```

게임은 현재 레시피와 상태를 기준으로 필요한 세부 행동을 결정한다.

### 4단계 후보: 개별 제작 명령

한 슬라임에게 최종 제작물을 직접 지정한다.

```text
"말랑아, 테스트용 마법서 만들어."
```

슬라임은 레시피에 필요한 세부 행동을 순서대로 수행한다.

다만 이 단계는 자동화 범위가 지나치게 커지면 플레이어의 개입을 줄일 수 있으므로, 실제 채택 여부는 펀테스트 이후에 판단한다.

---

## 5. 명령 확장의 의도

명령 확장의 핵심은 같은 슬라임에게 더 큰 작업 단위를 맡길 수 있게 되는 것이다.

```text
초반
현장의 행동을 하나씩 지시한다.

중반
여러 행동을 한 문장으로 묶는다.

후반 후보
세부 동작이 아니라 작업이나 제작 목표를 지시한다.
```

플레이어는 다음처럼 변화한다.

```text
행동을 하나씩 지정하는 사람
→ 작업 순서를 묶어 지시하는 사람
→ 제작 목표를 전달하고 진행 상태를 관리하는 사람
```

능력치가 단순히 상승하는 것보다, 이전에는 여러 번 말해야 했던 일을 더 짧고 큰 단위의 명령으로 처리하게 되는 것이 성장 경험의 후보로 제안됐다.

---

## 6. 그룹·스쿼드 명령 기각

다음과 같은 명령은 현재 방향에서 사용하지 않는다.

```text
"채집조, 초록 약초를 모아."
"제작조, 방어 주문서를 생산해."
"주방팀, 마법서 만들어."
```

### 기각된 이유

- 여러 슬라임의 역할 편성과 작업 분배가 추가로 필요하다.
- 더 넓은 맵과 더 많은 생산 시설이 필요해질 가능성이 높다.
- 작업 배분 AI와 예외 처리까지 구현 범위가 확장된다.
- 플레이어가 한 번 명령한 뒤 자동 진행을 구경하는 구조가 될 수 있다.
- 남은 개발 기간에 비해 구현과 밸런싱 범위가 지나치게 커진다.
- 현재 확인하려는 핵심은 집단 자동화가 아니라 음성으로 개별 슬라임을 움직이는 행위의 재미다.

따라서 현재 음성인식 설계는 **개별 슬라임 지정**을 기본으로 유지한다.

---

## 7. 생산 위계에 대한 논의

더 큰 작업 단위의 명령이 의미 있으려면 작업 자체에도 어느 정도 위계가 있어야 한다는 의견이 나왔다.

단순한 레시피가 다음으로 끝난다면,

```text
원재료 가져오기
→ 한 번 조합하기
→ 완성
```

작업 명령이나 제작 명령을 해금했을 때 압축되는 행동 수가 적다.

명령 추상화가 체감되려면 다음과 같은 구조가 필요할 수 있다.

```text
원재료 A
→ 중간 작업 B
→ 완성품 C
```

예시:

```text
초록 약초 투입
→ 섞어서 약액 만들기
→ 양피지 담그기
→ 마법서 완성
```

그러면 명령은 다음처럼 달라질 수 있다.

```text
초반
"약초 가져와."
"가마솥에 넣어."
"섞어."
"양피지를 담가."

후반 후보
"테스트용 마법서 만들어."
```

다만 중간재 종류와 생산 단계를 계속 늘리면 유사 공장 게임 규모로 커질 수 있으므로, 현재는 단일 레시피 안의 순차 작업 정도만 사용한다.

---

## 8. 명령 추상화 구조의 위험

### 8.1 범위가 지나치게 커질 수 있음

작업 또는 제작 단위 명령을 본격적으로 만들려면 다음 요소가 필요해질 수 있다.

- 여러 단계의 생산 공정
- 중간 상태와 완성 상태
- 다양한 제작 시설
- 명령을 세부 행동으로 분해하는 규칙
- 진행 중 명령 취소와 수정
- 시설 상태에 따른 예외 처리
- 명령 큐와 작업 기억
- 여러 레시피의 충돌 처리

현재는 이 요소들을 모두 만들지 않는다.

### 8.2 자동화가 게임을 없앨 수 있음

다음 한마디로 제작 전 과정이 완벽하게 해결되면,

```text
"말랑아, 테스트용 마법서 만들어."
```

플레이어가 가마솥 상태나 작업 타이밍을 관리할 이유가 사라질 수 있다.

따라서 제작 명령을 도입하더라도 다음 중 일부는 플레이어가 계속 판단하게 해야 한다.

- 어느 가마솥을 사용할지
- 어떤 작업을 먼저 할지
- 완성품을 언제 꺼낼지
- 진행 중인 작업을 취소하거나 바꿀지
- 여러 시설 중 어디에 슬라임을 보낼지

고차원 명령은 플레이를 제거하는 완전 자동화가 아니라, 반복 발화를 줄이면서도 판단은 남기는 방향이어야 한다.

### 8.3 단순 반복량 증가로 음성을 강제하면 피로해질 수 있음

초반에는 1개, 후반에는 100개를 만들게 해서 긴 명령을 강제하는 방식은 음성인식의 필요성은 만들 수 있지만, 플레이어에게 반복 노동으로 느껴질 수 있다.

따라서 명령 확장을 도입한다면 단순 수량 증가보다 다음이 중요하다.

- 작업 순서의 변화
- 시설 타이밍 관리
- 잘못된 상태에서 명령했을 때의 대응
- 진행 중인 작업과 다음 작업의 선택
- 명령을 얼마나 묶을지에 대한 판단

## 9. 슬라임의 청력과 집중력

기존 문서에서는 음성 명령과 관련된 스탯으로 청력과 집중력을 제안했다.

### 청력

- 플레이어의 명령을 들을 수 있는 거리를 결정한다.
- 범위 밖에서는 `NOT_HEARD`로 처리한다.
- 듣지 못한 명령을 다른 행동으로 잘못 수행하게 만들지 않는다.
- 플레이어가 슬라임 가까이 이동해야 하는 공간적 이유를 만든다.

### 집중력

- 슬라임이 기억할 수 있는 원자 작업 수를 결정한다.
- 연속 명령은 세부 행동으로 분해한 뒤 필요한 작업 수를 계산한다.
- 한도를 넘으면 `TOO_COMPLEX`로 처리한다.
- 작업 중 새 명령을 받았는데 기억 공간이 부족하면 `QUEUE_FULL`로 처리한다.

### 현재 상태

청력과 집중력은 기존 설계에 존재하지만, 이번 펀테스트의 핵심 검증 대상에서는 우선 제외하거나 고정값으로 처리한다.

음성 조작 자체가 재미있는지 확인하기 전에 낮은 청력이나 집중력으로 명령을 거부하면, 플레이어가 음성 시스템 자체를 불편하게 평가할 수 있기 때문이다.

---

## 10. 음성인식과 마탑·공방 콘셉트

일반 식당보다 마탑 또는 마법 공방이 음성 명령과 더 자연스럽게 어울린다는 의견이 나왔다.

### 설정 연결

- 플레이어: 마법사 또는 공방 관리자
- 슬라임: 사역마 또는 공방 일꾼
- 음성 명령: 지시이자 주문
- 레시피: 마법 제작법
- 마법서: 제작물
- 작업대: 가마솥
- 완성품 제출: 제출대 또는 납품 마법진

이 설정에서는 플레이어가 마이크로 슬라임에게 말하는 행위가 세계관 안에서 자연스럽게 해석된다.

---

## 11. 현재 결론: 완성형보다 펀테스트 우선

명령 추상화와 생산 위계를 논의한 결과, 이를 완성형 시스템으로 바로 구현하면 범위가 커질 수 있다는 데 의견이 모였다.

따라서 현재는 다음 순서를 따른다.

```text
1. 음성으로 개별 슬라임을 움직이는 기본 경험을 만든다.
2. 실제 플레이에서 재미가 있는지 확인한다.
3. 재미가 확인된 경우에만 연속 명령과 작업 단위 명령을 추가 검토한다.
```

현재 검증하려는 핵심 가설은 다음이다.

> 화면을 보며 개별 슬라임에게 말로 작업을 지시하고, 슬라임이 그 명령에 반응하는 과정 자체가 재미있는가?

## 12. 현재 펀테스트에서의 음성인식 범위

### 테스트 구성

- 제한 시간: 3분
- 목표: 테스트용 마법서 8장 제작
- 슬라임: 1마리
- 가마솥: 2개
- 재료: 초록 약초, 양피지
- 완성품: 테스트용 마법서
- 주문 생성 시스템 없음
- 업그레이드 없음
- 그룹 명령 없음
- 스쿼드 없음
- 슬라임 종류별 성장 없음

### 테스트용 제작 흐름

```text
1. 슬라임에게 초록 약초를 가져오라고 명령한다.
2. 가마솥에 약초를 넣도록 명령한다.
3. 섞는 작업을 명령한다.
4. 5초 동안 기다린다.
5. 양피지를 가져와 담그도록 명령한다.
6. 5초 동안 기다린다.
7. 완성된 마법서를 꺼내도록 명령한다.
8. 제출용 테이블로 운반하도록 명령한다.
```

두 가마솥의 작업 시간이 동시에 흐르므로, 플레이어는 슬라임 한 마리에게 어떤 일을 먼저 시킬지 판단해야 한다.

이번 테스트에서는 다음을 확인한다.

- 이름과 행동을 말하는 것이 자연스러운가
- 슬라임이 명령에 반응하는 모습이 재미있는가
- 한 슬라임에게 반복해서 작업을 지시하는 것이 피로하지 않은가
- 가마솥 두 개의 상태를 관리하며 다음 발화를 계획하는 것이 재미있는가
- 음성 입력 지연과 실패가 게임 흐름을 심하게 끊지 않는가
- 연속 명령이 없어도 기본 플레이가 성립하는가
- 연속 명령이 필요하다는 요구가 플레이 중 자연스럽게 발생하는가

---

## 13. 펀테스트에서 필요한 피드백

음성 명령의 성공과 실패를 플레이어가 즉시 이해할 수 있어야 한다.

### 화면에 표시할 정보

- 인식된 문장
- 해석된 슬라임 이름
- 해석된 행동
- 해석된 대상
- 명령 성공 여부
- 실행할 수 없는 이유
- 현재 슬라임의 행동
- 가마솥의 현재 상태와 남은 시간

### 구분해야 할 실패

```text
NOT_HEARD
슬라임이 명령을 듣지 못함

UNKNOWN_ACTOR
지정한 슬라임을 찾지 못함

UNKNOWN_ACTION
지원하지 않는 행동

UNKNOWN_TARGET
대상을 찾지 못함

INVALID_STATE
현재 상태에서는 실행할 수 없음

TOO_COMPLEX
명령이 현재 지원 범위보다 복잡함

QUEUE_FULL
슬라임이 더 이상 작업을 기억할 수 없음
```

펀테스트에서는 모든 오류를 구현할 필요는 없지만, 적어도 다음은 구분해야 한다.

- 음성을 제대로 인식하지 못함
- 문장은 인식했지만 게임 명령으로 해석하지 못함
- 명령은 유효하지만 현재 상황에서 실행할 수 없음
- 명령을 정상적으로 접수해 실행 중임

---

## 14. 펀테스트 성공 신호

다음 반응이 관찰되면 음성 조작의 가능성이 있다고 본다.

- 플레이어가 자발적으로 슬라임의 이름을 부른다.
- 명령 성공 시 슬라임의 반응을 보고 만족하거나 웃는다.
- 기다리는 동안 다음 명령을 미리 생각한다.
- 두 가마솥을 번갈아 운영하며 바빠지는 상황을 즐긴다.
- 마우스 조작이 가능하더라도 음성을 계속 사용하려 한다.
- 실수했을 때 시스템보다 자신의 작업 순서나 타이밍을 탓한다.
- 한 판이 끝난 뒤 다시 하면 더 잘할 수 있을 것 같다고 느낀다.
- 여러 행동을 한 문장으로 묶고 싶다는 욕구가 자연스럽게 생긴다.

---

## 15. 위험 신호

다음 반응이 많으면 콘텐츠를 확장하기 전에 음성 조작부터 수정해야 한다.

- 처음 한두 번만 신기하고 이후에는 말하기를 귀찮아한다.
- 명령을 내리기 전에 정답 문법부터 고민한다.
- 인식 결과를 기다리느라 플레이 흐름이 멈춘다.
- 슬라임이 무엇을 하는지 몰라 같은 말을 반복한다.
- 바빠질수록 재미보다 발화 피로가 커진다.
- 마우스가 있었으면 훨씬 편했을 것이라고 느낀다.
- 인식 실패가 자신의 실수보다 게임의 억울함으로 느껴진다.
- 명령에 성공해도 슬라임의 반응이 밋밋해 성취감이 없다.
- 연속 명령이 없어서 불편한 것이 아니라 음성 자체를 쓰기 싫다고 느낀다.

---

## 16. 펀테스트 이후 가능한 비교 실험

첫 테스트가 긍정적이라면 슬라임 수를 늘리는 대신, **같은 슬라임에게 허용하는 명령 단위만 바꾸어 비교한다.**

### A안: 단일 행동만 허용

```text
"말랑아, 약초 가져와."
"말랑아, 1번 가마솥에 넣어."
```

### B안: 연속 명령 허용

```text
"말랑아, 약초 가져와서 1번 가마솥에 넣어."
```

### 비교할 항목

- 연속 명령이 실제로 발화 피로를 줄이는가
- 명령이 길어졌을 때 인식 오류가 늘어나는가
- 행동이 묶이면서 플레이어의 판단이 줄어들지는 않는가
- 단일 행동보다 더 지휘하는 느낌이 드는가
- 어느 길이까지 한 문장으로 말하는 것이 자연스러운가

이 테스트에서 연속 명령이 분명한 장점을 보일 때만 작업 단위 명령이나 제작 명령을 추가 검토한다.

## 18. 현재 확정된 것과 미확정된 것

### 비교적 확정된 것

- 음성인식은 게임의 핵심 조작 방식이다.
- 오디오를 Gemini가 명령 JSON으로 구조화한다.
- 실제 행동과 상태 판정은 게임 코드가 담당한다.
- AI가 임의의 게임 요소를 생성하지 못하도록 후보를 제한한다.
- 현재는 음성 조작의 기본 재미를 먼저 검증한다.
- 펀테스트에서는 슬라임 1마리와 단일 행동 중심 명령을 사용한다.
- 그룹·스쿼드 단위 명령은 사용하지 않는다.
- 업그레이드와 명령 추상화는 펀테스트 이후에 판단한다.
- 마탑·공방 콘셉트는 음성 명령의 당위성과 잘 맞는다.

### 아직 결정되지 않은 것

- 음성 조작 자체가 실제로 재미있는가
- 첫 버전에서 연속 명령까지 허용할 것인가
- 한 번의 발화에 몇 개의 행동을 허용할 것인가
- 음성 처리 지연을 어느 정도까지 허용할 수 있는가
- 청력과 집중력 스탯이 재미를 더하는가
- 작업 단위 명령이 실제 성장 시스템으로 필요한가
- 제작 명령 이후에도 플레이어가 계속 판단할 일이 남는가
- 자연어의 자유도를 높일지, 제한된 문법을 명확히 제시할지
- 음성 입력과 마우스 입력을 함께 허용할지

---

## 19. 한 문장 요약

> 음성인식은 마우스를 단순히 대체하는 입력 수단이 아니라, 개별 슬라임에게 내리는 단일 행동 명령을 연속 행동이나 작업 단위 명령으로 확장하는 핵심 조작 후보로 논의됐으며, 그룹·스쿼드 단위 명령은 범위와 자동화 문제로 기각하고 현재는 슬라임 한 마리와 가마솥 두 개를 이용한 3분짜리 펀테스트로 말로 지시하는 행위 자체가 재미있는지 먼저 검증하기로 했다.
