# 확정과 미정

> 이 문서는 **Claude가 작성했다** (2026-08-02). 사용자와의 회의에서 나온
> 결정을 옮긴 것이며, Claude가 새로 만든 기획이 아니다. 결정 내용에
> 의문이 있으면 이 문서가 아니라 사용자에게 확인해야 한다.

2026-08-02 회의 결과다. `[회의]`는 덱에 없고 회의에서 정해진 것,
`[덱↔회의]`는 덱 내용과 회의 결정이 다른 것이다.

## 1. 확정

### 화재는 설비 단위다 `[덱↔회의]`

덱 9장의 감점 항목 이름이 `화재 타일`이라 바닥 타일 화재로 읽힐 여지가
있었다. **"타일"은 세는 단위이고 대상은 설비끼리의 화재**다.

`raw/클로드_담당_작업_주문과_화재.md` §9·§14가 바닥 타일 화재를 제외한
것과 같은 뜻이며, 현재 구현이 이미 그렇다. 인접 판정은 설비 배치 거리로만
하고 바닥 타일은 전파 경로에서 빠져 있다.

### 점수 시스템을 넣지 않는다 `[덱↔회의]`

덱 9·10장은 점수 정산이 결과 화면의 중심이지만 **점수는 도입하지 않는다.**
`raw/클로드_담당_작업_주문과_화재.md` §2의 "돈, 수당, 점수 시스템을
추가하지 않는다"가 유효하다.

### 정산 합계 자리에는 골드를 쓴다 `[회의]`

점수를 빼는 대신 이미 게임에 있는 골드를 합계 자리에 표시한다.
주문 완료마다 100G가 쌓이는 현재 동작을 그대로 쓴다.

### 랭킹을 넣지 않는다 `[덱↔회의]`

덱 2장의 랭킹 시스템(최고 스테이지 / 최고 제작 횟수 / 동률 시 선클리어)은
도입하지 않는다. 덱에도 "안 넣어도 되는데"라는 단서가 있었다.

### 화재로 인한 손실은 없고 정산에도 올리지 않는다 `[덱↔회의]`

덱 9장의 `화재 타일` 감점 행은 **정산 화면에서 뺀다.** 화재로 골드가
줄지 않는다.

`raw/클로드_담당_작업_주문과_화재.md` §11 "화재로 인한 수당 감소나 돈
차감은 구현하지 않는다", §14 "화재로 인한 돈 또는 수당 감소" 제외와
같은 방향이다.

화재 자체는 그대로 남는다. 불난 설비를 쓸 수 없고 물 슬라임이 꺼야 하는
압박이 페널티이며, 별도의 재화 손실을 얹지 않는다.

### 슬라임 죽음을 넣지 않는다 `[덱↔회의]`

덱 9장의 `슬라임 죽음` 감점 항목은 쓰지 않는다. 죽는 조건이 어느 문서에도
정의돼 있지 않고, `raw/클로드_담당_작업_주문과_화재.md` §14도 슬라임
사망을 제외했다.

### 슬라임 명칭은 땅이다 `[덱↔회의]`

덱과 아트는 `풀 슬라임`(새싹)이지만 확정 명칭은 **`땅 슬라임`**이다.
코드의 `earth`를 그대로 둔다.

> 남은 문제: 덱의 아트가 새싹 모양이라 이름과 그림이 어긋난다. 아트를
> 땅 느낌으로 바꿀지, 그림은 두고 이름만 땅으로 갈지 정해야 한다.

### 같은 속성을 여러 마리 데려올 수 있다 `[회의]` — 구현 완료

영입 화면에서 **이미 데려온 속성도 다시 고를 수 있다.** 따라서 후보는 항상
4종이고 카드가 비는 경우가 없다.

2026-08-02 구현했다. 슬라임을 속성이 아니라 인스턴스 ID(`water-1`,
`water-2`)로 식별하고, 같은 속성이 둘 이상일 때만 이름에 `2호`처럼 번호가
붙는다. 속성 키(`Q/W/E/R`)는 그 속성의 모든 마리를 한 번에 고른다.

### 스테이지 구조를 넣는다 `[회의]`

덱 4장의 화면 전개를 실제로 구현한다. 현재는 3분 단일 라운드뿐이라
게임 루프 자체가 바뀌는 가장 큰 작업이다.

## 2. 아직 정하지 않은 것

### 주문 실수를 정산에 올릴지

점수·죽음·화재를 빼면 덱의 4행 표에서 남는 것은 **주문 성공**과
**주문 실수** 둘뿐이다.

| 항목 | 상태 |
|---|---|
| 주문 성공 | 확정. 완료 1건당 100G |
| 주문 실수 | **미정** |
| 슬라임 죽음 | 제외 |
| 화재 타일 | 제외 |
| 합계 | 확정. 골드 |

주문 실수에 대해 정해야 할 것:

- 정산에 올릴지, 아예 빼서 성공 한 줄만 둘지
- 올린다면 골드를 깎을지, 횟수만 보여줄지

지금 게임에는 **주문 실수 횟수를 세는 카운터가 없다.** 올리기로 하면
`submitFood`의 거부 경로에 카운터 한 줄이 붙는다.

성공 한 줄만 남기면 정산 화면은 사실상 "이번 라운드에 몇 건 벌었다"가
되고, 덱의 표 형태를 유지할 필요가 없어진다.

### 스테이지 한 판을 무엇으로 적을 것인가

덱은 `1-1`부터 `3-3`까지 여러 스테이지를 만든다고 한다. 스테이지마다
코드를 새로 짤 수는 없으니, **스테이지 하나를 설명하는 목록을 정해 두고
스테이지마다 그 목록만 채우는** 방식이 필요하다. 이 목록에 무엇이
들어가야 하는지가 아직 정해지지 않았다.

예를 들어 이런 식이 된다.

```
1-1 스테이지
  이름          "첫 손님 맞이"
  TIP           "버섯은 불 슬라임이 구워요"
  나올 음식      버섯 구이
  주문           버섯 구이 3개
  제한 시간      3분
  클리어 후      슬라임 영입 있음
```

`2-1`을 추가할 때는 같은 항목을 다른 값으로 한 벌 더 쓰면 되고, 코드는
건드리지 않는다.

무엇을 목록에 넣을지 후보와 근거:

| 항목 | 근거 | 비고 |
|---|---|---|
| 번호·이름 | 덱 5장 (`3-3 : …`) | 30자 이내 |
| TIP 문구 | 덱 5장 | 2줄, 30자 이내 |
| 나올 수 있는 음식 | 덱 5장 | 슬롯 6칸 |
| 주문 | 덱 9장 | 이미 외부에서 넣을 수 있게 돼 있어 그대로 얹힌다 |
| 제한 시간 | 현재 3분 고정 | 스테이지마다 다르게 할지 미정 |
| 클리어 후 영입 여부 | 덱 4장 루프 | 매 스테이지인지 특정 구간인지 미정 |

이 목록이 정해지면 스테이지 루프와 정산 화면이 함께 풀린다. 반대로
정해지지 않으면 어느 쪽도 시작할 수 없다.

### 스테이지당 음식이 6종을 넘을 수 있나

덱의 음식 목록 슬롯이 6칸 고정이다. 넘는 스테이지가 생긴다면 스크롤인지
페이지인지 정해야 한다.

### 스쿼드 상한

현재 코어는 스폰 자리 수(4)를 상한으로 쓴다. 스테이지마다 영입이 쌓이면
5마리 이상이 되는데, 상한을 올릴지 스폰 자리를 늘릴지 정하지 않았다.

### 화재 발생까지의 시간

`fireConfig.igniteAfterMs`가 12초다. 브라우저 플레이에서 조리 완료 직후
바로 타는 편이라 펀테스트로 값을 정해야 한다. 상수 한 줄이다.

### 화재 진압 후 복구 시간

`raw/클로드_담당_작업_주문과_화재.md` §18의 미정 항목이며 규칙이 없어
설정도 코드도 만들지 않았다.

## 3. 작업 순서 제안

1. **스테이지 한 판의 항목 확정** — 위 표를 채우면 2·3이 한 번에 풀린다
2. **스테이지 루프와 화면 전환** — 소개 → 인게임 → 정산 → 영입
3. **정산 화면** — 1·2가 있어야 보여줄 내용이 생긴다

영입 화면이 없어 지금은 UI에서 중복 스쿼드를 만들 수 없다. 2번에서
자연스럽게 열린다.
